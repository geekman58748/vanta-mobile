## Act 1 — The spec

Privacy wallet on Solana; core = private send via **Umbra SDK on Arcium MPC**;

**User asked:** "what's arcium and how does it work with umbra?"
**Agent explained:** Arcium = decentralized MPC network on Solana (multiple nodes
jointly compute over encrypted state; no single node sees full data). Umbra = SDK on
top exposing register / shield (ATA→ETA) / private transfer / unshield. Different
from MagicBlock (TEE/hardware trust) — do not conflate.

**Phase 3 check:** `npm view @umbra-privacy/sdk versions --json` → public, latest
`5.0.0-rc.10`. Docs at sdk.umbraprivacy.com: devnet endpoints + dUSDC mint confirmed
(see HANDOFF §4.1).

## Act 4 — "Where is my 0.9 SOL?" — the deposit-is-not-a-send crisis

**User sent 0.9 back to Solflare** with Private ON. Console showed deposit success
(`21ShjaqYgE...`), but **Solflare never received it**. Solscan for the callback tx
(`mDA1akWpSZ...`) showed success with tiny fees — nothing at the recipient.

**Root cause:** the app's "send" was wired to `depositATAIntoETA` — shielding into
the user's own encrypted account. Not a transfer at all. Agent initially added a
"Withdraw from Pool" button (Umbra withdrawal module) to recover funds.

**User (angry, correctly):** "wtf is going on? why should a private send be this
complex? why should a user have to click withdraw from pool? … I'm trying to send to
an address using privacy; the recipient shouldn't know where it came from."

Agent pivoted to **self-burnable stealth notes**:
`getATAIntoSelfBurnableStealthPoolNoteCreatorFunction` + scan +
`getSelfBurnableStealthPoolNoteIntoATABurnerFunction`. Console after first note:
`Self-burnable stealth note created: {populateProofAccountSignature: '3vsod6kkXapT1p9zeaYsnXGQf5fpsebo4aAzbUMqraaJjMhxZ8a2n33GnbGLzPzWME1XfVqSj6ZdTVMtwFVAGZjN', createUtxoSignature: '3FVFh71oa9ibbttdG2naegchQCtC1JDFZbjNPY4cx38E8UgTCyg4a7eJbPMzx3FhD2Y6VLmJgFpgNohKG7VTsQbZ', signatures: Array(2)}`

But funds still didn't arrive at the recipient — flow needed scan+burn. Agent floated
a "Claim" page; **user rejected any recipient-side action**: "imagine telling a human
to connect a wallet to claim funds? go dig up any docs you can, this must work."

Agent dug into the SDK's burn module: the self-burnable-into-ATA burner signs the
burn with a **one-time ephemeral signer derived from the master seed** and pushes
through **Umbra's relayer** → recipient's public wallet gets funds with zero
recipient action. That wiring was implemented (relayer `submitClaim`/`pollClaimStatus`/
`getRelayerAddress`) and **verified live**: user private-sent 0.1; console showed note
created then burn flow; **Solflare received 0.099652 SOL from an unknown address.**

  `3n1MVbXiHpkweM8RZebYcgKWv44pVhfynzwPtvFvYWoc`**.
- That account's signature history = the sender's deposit txs (`5F6B8yAeAbCE…`,

## Act 6 — The fix: per-send burner wallet (current architecture)

`privateSend` rewritten (see App.jsx): fresh burner Keypair per send (persisted to
`localStorage['vanta-burner-<fundSig>']` for recovery), funded by main wallet with
amount + 0.02 buffer; **burner** gets its own Umbra client + confidential
registration; burner shields; scan (10 retries × 3s); burn into recipient's public
wallet via relayer. Main wallet and its linker PDA never touch pool/claim txs.

Post-fix state: built, deployed, live on `http://localhost:3000`. **E2E re-test of
the burner flow is the next agent's first job** (procedure in HANDOFF §6).
