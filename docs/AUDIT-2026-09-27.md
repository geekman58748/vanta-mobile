# Vanta — adversarial audit (emulator, devnet) — 2026-09-27

> **Scope.** Live app (`com.vanta.privacywallet`, debug shell on `emulator-5554`) driven over CDP,
> real devnet, real relayer (`:3001`) and the deployed Northflank relayer. Every flow exercised:
> 5× Shield, 1× Ghost, 1× public send, 1× Shadow (by `.vanta` name), 1× Shadow→unregistered,
> MWA connect + authorize, name claim, app-data wipe. Chain evidence pulled with
> `getTransaction`, DB evidence read directly, APK evidence read from `vanta-1.0.0-ux5.apk`.
>
> **What this is not.** No fixes were applied. Line numbers are from the working tree at audit time.
> All funds are devnet and all keys used are throwaway test identities.

---

## Verdict

The **rails and the recording path are real and work** — 5/5 Shields, Ghost, public send and a
name-resolved Shadow all landed and were confirmed on chain; `verified_on_chain = true` for all
three spend types; the relayer's auth caps, rate limits and claim-proof checks all hold. The
product claim of honesty is mostly honoured in the UI copy.

The problems are **not in the crypto. They are in the custody, the storage and the trust boundary
around the server** — and three of them are directly fatal to the privacy thesis if a
security-researcher judge opens the APK.

---

## 🔴 CRITICAL

### C1. The relayer token ships inside the APK, and it unlocks the private payment graph
`VITE_RELAYER_TOKEN` is compiled into the client bundle (`VITE_*` is inlined at build time), so
the token is extractable from the public APK:

```
unzip -p deploy/releases/vanta-1.0.0-ux5.apk 'assets/www/assets/index-*.js' | grep -o 6b630b91…
→ found
```

That token is the **live production token**. Without it the deployed relayer answers `401`;
with it, `200` and the full history:

```
GET /tx/4v5T58hW… — x-vanta-token: <from APK>
→ {"count":6, "transactions":[{"flow":"shadow",
     "actors":["4v5T58hW…"], "counterparty":"9b4j2Fen…",
     "amount_atomic":"50000000", "block_time":"2026-09-27T22:08:22Z", …}]}
```

**Impact.** The entire value proposition of a Shadow send is that the recipient and amount are not
derivable from chain data. This makes them derivable by anyone who downloads the APK. The sender
identity is *already* public (it is the fee payer on every spend, PLAN §3.1), so the attack chain is
complete: read the fee payer from an explorer → query the relayer with the extracted token → get
recipient and amount. No key, no exploit, no auth bypass — just unzip.

### C2. The server stores exactly the linkage the pool hides, and the app promises it doesn't
For every Shadow/Ghost send the client `POST`s, and Postgres keeps, `actors:[X]`,
`counterparty:<recipient address>`, `amount_atomic`, and timestamps in plaintext:

```json
{"flow":"shadow","actors":["4v5T58hW…"],"counterparty":"9b4j2Fen…",
 "amount_atomic":"50000000","client_report":{"mode":"Shadow"}}
```

Meanwhile the Activity sheet tells the user: *"Vanta keeps no server-side history, so a reload
starts the week over."* The relayer keeps the **most sensitive** history in the product, and the
honesty surfaces (`lib/honesty.js`, the receipt rows) never mention it. For a product whose thesis
is "every claim has a tx hash, and we tell you what leaks", this is the one leak that is not
disclosed anywhere.

### C3. The shielded spend key is plaintext in `localStorage`, and the snapshot encryption is decorative
```
vanta-ephemeral : {publicKey, secretKey: array[64]}     ← plaintext, the key that spends the private balance
vanta-zwallet   : {v, snapshotVersion, nonce, data}     ← "encrypted" with a key derived from the above
```
Because the seed sits beside the ciphertext, the `vanta-zwallet` encryption buys nothing against a
local attacker. Any rooted device, ADB backup, malicious app with WebView data access, or XSS in
the shell = silent, complete drain of the private balance. The footer discloses "keys live in this
browser's localStorage only" — the wording is honest about *where*, not about *how*.

## 🟠 HIGH

### H1. All history and receipts vanish on every restart — while the server has them
`pm clear`-free, plain **app restart**: `localStorage` has no transaction keys (`txKeys: []`), the
dashboard reads **"No transactions yet."**, and the 5 Shields + Ghost + Shadow + public send from
this session are gone. The receipts — the flagship artefact, each backed by a tx hash — cannot be
re-opened or re-exported. The rows exist in the relayer (`/tx/X` → 6 rows, `/tx/wallet` → 11) and
are **keyed to X, not to the wallet**, so rehydration was possible but is not implemented.
Consequence: beta-test flow #8 ("every tx above is listed and matches the chain") fails for anyone
who restarts the app, and the "Download PDF receipt" affordance is only reachable in the minutes
after a send.

### H2. "Download PDF receipt" reports success and writes nothing
Tapped on a real receipt on-device:
```
toast:  "Saved vanta-public-receipt-2026-09-27.pdf"     ← fires at t+2s
disk:   nothing. Not /sdcard/Download, not the app's external files dir,
        not anywhere on the device (searched).
```
The WebView silently drops the data-URL anchor download; the handler only knows the click didn't
throw, so it toasts success. The Node/desktop harness (`scripts/pdf-receipt-check.mjs`) cannot catch
this because desktop Chrome accepts what the WebView drops. A false success confirmation is worse
than a failure: the user believes they hold proof they don't.

### H3. The advertised "falls back to a Ghost send" never fires
`SendDrawer.jsx:144` falls back only when the error message contains `RECIPIENT_NOT_REGISTERED`.
The SDK wraps the failure: `wallet/transactions.ts:73` throws `WALLET_BUILD_TRANSFER` over the
cause, so the match never happens. Observed on-device sending Shadow → an unregistered address:

```
MSG::Failed: WALLET_BUILD_TRANSFER
```

The drawer's own copy promises the fallback ("If they aren't registered, this falls back to a Ghost
send"). Today the user gets a dead send and a raw internal error code. (The broken fallback is also,
perversely, the only thing preventing a silent privacy downgrade — see M2.)

### H4. No backup path: clearing data destroys the shielded balance permanently
Demonstrated end-to-end. Before: identity `4v5T58hW…`, private balance **0.150 SOL**. Then
`adb shell pm clear com.vanta.privacywallet` → relaunch →
`localStorage: []`, onboarding shown, identity gone. The 0.150 SOL is unrecoverable: no export, no
seed reveal, no restore — `grep` for backup/export/reveal in `src/` returns nothing but copy.
Uninstall does the same. `BETA-TEST.md` flags this correctly; this audit is the reproduction.

### H5. Incoming funds never update the displayed balance
External funding is invisible until a full app restart:
- relayer `/fund` +0.2 SOL → app still showed **0.100** for 2+ minutes (chain: 0.300)
- "Force resync from chain" does **not** fix it (that only rescans private notes)
- a Ghost payout *to the app's own wallet* didn't move the public figure either
- only `location.reload()` corrected it to 0.300

The Shield drawer's "Public balance" and fee-aware **Max** are computed from this stale number, so a
user who has just been funded can be told they can't shield. Recovery (kill and relaunch) is
undiscoverable mid-demo.

### H6. Connecting MWA silently replaces the public wallet and strands the old one
Clicking Connect → fakewallet AUTHORIZE → the public address changed from the session wallet
`CfborKae…` to the device wallet `CYqVimCp…` with **no warning**. `vanta-wallet` was overwritten
(`{publicKey, mwa:true, label}` — the old secret is gone), leaving **0.099995 SOL orphaned** in an
address the UI no longer references and the app can never spend. Privacy identity X and the private
balance survived (good), but the public side of the wallet teleported.

## 🟡 MEDIUM

### M1. The Receive sheet hands your address to a third party
`ReceiveDrawer.jsx:13` builds the QR as
`https://api.qrserver.com/v1/create-qr-code/?…&data=solana:<publicKey>`. Opening Receive sends the
address (and the device IP) to a free QR service. Secondary effect: **the QR is broken offline** —
the APK is otherwise fully offline-capable. The Vanta (private) address has no QR at all.

### M2. Claims vs behaviour (three small lies)
- Activity sheet: *"Vanta keeps no server-side history"* — false (see C2).
- Ghost-to-self receipt: *"Your public wallet is absent from this leg"* — false when the recipient
  **is** your own public wallet (that is exactly the self-ghost the beta test runs).
- Shadow drawer: the fallback promise in H3.

### M3. Raw internals shown to users
`Failed: WALLET_BUILD_TRANSFER`; `Airdrop failed: airdrop to CfborKae… failed: Internal error`.
Neither tells a user what to do. `shieldErrorMessage` proves the app knows better — the send path
just doesn't use it.

### M4. Test data in the production database
The DB harness's placeholder row is still there:
`HarnesstestSignatureThatDoesNotExist1111… / flow: shadow / actors: [someUnrelatedAddress111…]`.
It shows up in `/tx/` responses if that key is ever queried, and it is a permanent reminder that the
harness ran against the live DB.

### M5. Accessibility: receipts are unreachable without touch
Activity rows are plain `<div>`s (`justify-between py-3 …`) with no `role`, no `tabindex` and no
keyboard handler, yet the analytics sheet instructs "Tap any row for its on-chain reference." The
single most product-defining affordance is not focusable or screen-reader labelled.

### M6. Privacy mode is easy to misunderstand, and doesn't persist
The dashboard toggle (Shadow ↔ Ghost) silently changes the semantics of the Send button, resets to
Shadow on restart, and in Ghost mode a low-contrast secondary button ("or send plain public SOL →")
performs an immediate **public** send with the same recipient/amount — the sender identity becomes
the wallet. No pre-confirmation of the downgrade in either path.

## 🟢 LOW / cosmetic

- **L1** The daily header shows `+0.000 / -0.000` with zero activity — empty-state noise.
- **L2** The `.vanta` handle still isn't shown in Receive / Profile-receive (the PLAN P0 polish
  item), so a sender can't discover your handle without being told it.
- **L3** The test harness's own console noise: repeated `Blocked call to navigator.vibrate` (an
  artefact of synthetic clicks, not of real users).
- **L4** Unknown API paths return Express's HTML 404 (`Cannot GET /etc/…`) instead of JSON —
  inconsistent surface, and it confirms path normalisation is doing the security work.
- **L5** `autoShield` is still labelled "Preview — not wired yet".

**association path has no timeout** (`withTimeout` wraps only `signTransaction` /
`signAndSendTransaction`, `mwa.js:138,153`), so if the wallet never answers the UI spins forever
with no error and no retry. Signing is protected; connecting is not.

## 🚀 Where the remaining upside is

Ranked by (demo impact ÷ effort), with the caveat that the first two are **trust-model** work, not
features — they convert the critical findings into a selling point.

1. **"Your receipts can't be read, even by us."** Move history to client-side encrypted storage and
   authenticate reads per-identity (signed request, not a shared bearer token). Kills C1, C2, M1 and
   H1 at once, and becomes the natural second half of the honesty pitch: the server sees fees, not
   payments. Also re-enables reopening and re-exporting a receipt months later.
2. **Seed Vault custody on Seeker** (already the stated direction). Replaces the plaintext seed (C3)
   and gives a real answer to H4 — backup/restore that a phone can actually hold — and it is the
   Seeker-native reason to keep the app installed.
3. **Rotating receive identities.** Today the displayed "Vanta address" *is* the spend identity, so
   anyone you receive from can chart every send you make afterwards. A per-counterparty receive key
   (or a receive-only key that cannot pay fees) closes this and is a concrete, demoable privacy win
   over the current single-X design.
4. **Rings' two tiers as one product.** Helius's public framing is two-fold: a *public ring* where
   the amount is encrypted but parties are visible (MEV protection) and the *full ring*. Vanta ships
   the strong tier today; a tier-1 "pay anyone, amount hidden" mode — if the pinned SDK exposes it —
   makes Vanta the client that spans both, and aligning with Mert's own narrative is the safest
   judge-facing story.
5. **Incoming-shadow visibility for the recipient.** The recipient's private balance moves but the
   relayer has **zero** rows for them (`/tx/<bob>` → `count: 0`), and the app has no inbox. A local,
   encrypted "payments received" view (scanned from notes, never from the server) is a real product
   feature, not a fix.
6. **Recipient-side receipts.** Every privacy claim is currently proven from the *sender's* screen.
   Letting the receiver export "someone paid me 0.05 and the sender is not derivable" is the same
   evidence from the other side — and it is what a crowdfunding payout actually needs.
7. **Confidential swap via the rails' own prototype** (`sdk-tests/dynamic-swap`, hidden price and
   payout). The program is **not deployed on devnet** (verified: `getAccountInfo` → `null`), so this
   is roadmap, but it is the only swap story that fits the thesis — a Jupiter/Meteora swap would be
   devnet theatre against self-seeded liquidity.
8. **Seeker Genesis / SKR tier** — untouched today, and a separate prize. Highest-latency item.

### Suggested sequencing (audit opinion, not a plan)
H2/H5/H3 are demo-breaking and cheap → fix first. C1/C2/M1 are trust-model and cheap-to-medium →
before the repo is public, because they are the first thing a security-researcher judge will hit.
C3/H4 need the Seed Vault decision. Innovation items 3–6 all build on item 1, so doing item 1 first
makes them cheaper rather than additive.

## Coverage gaps (not tested, still open)

- Real wallet apps (Phantom / Solflare / Backpack) — v1 transaction support unverified; fakewallet v1
  was used throughout.
- Seeker hardware / Seed Vault path — not available.
- Physical-device behaviour for the PDF download (H2 reproduced on the emulator's WebView; the
  mechanism — a silent WebView download drop — is shell-level and expected to reproduce).
- Long-run relayer abuse beyond the observed window limit; `/relay` with a hand-crafted non-allowlisted
  program; DDoS-shaped abuse.
- `pm clear` **after** a funded Shield on a *physical* phone (equivalent here: 0.150 SOL orphaned).
